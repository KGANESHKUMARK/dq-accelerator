# AWS EMR integration — SYNTHETIC sample

> **SYNTHETIC** — no real EMR cluster, S3 bucket, or AWS credentials were used.
> These files show the *pattern* a spark-submit PySpark job follows before and
> after DQ Accelerator integration. Verified locally against the file-based
> harness, not a live EMR cluster.

| File | Purpose |
|---|---|
| `loans_pipeline_original.py` | Typical EMR spark-submit job: owns its SparkSession, `s3a://` parquet in/out |
| `loans_pipeline_dq_integrated.py` | Same job with the engine inserted inline (`«DQ INTEGRATION»` markers) |

Pairing assets in this repo:

- Manifest: `config/pipelines/EMR_LOANS_PIPELINE.yaml`
  (platform `STANDALONE_SPARK` — the manifest enum has no `EMR` value because
  EMR *is* standalone Spark; the id/description carry the EMR label)
- Sample data: `sample_data/bronze/loans.csv`
- Ruleset: `config/rulesets/loans_v1.yaml` (generated by `dqctl bootstrap`)

On a real EMR cluster: ship the wheel via `--py-files` (or bake it into the
AMI/venv), keep the config bundle on `s3a://`, and submit with `spark-submit`.
